# Fresh Grafana verification - 2 November 2026

Scope: native x86_64 Linux, InfluxDB 2.7.10, Grafana 11.3.0, repository amqtt fallback. This is not a Docker, ARM emulator, Raspberry Pi OS installation, or physical Raspberry Pi test.

## Reproduction sequence

With an isolated local InfluxDB instance configured for the book's `iotlab` organization and `sensor_data` bucket, and Grafana provisioned with the repository's Flux datasource and `dashboards/iot-ml-capstone.json`:

1. Run `python scripts/mqtt/run_broker.py`.
2. Run `python scripts/inference/train_capstone_iforest.py`.
3. Run `python scripts/subscribers/capstone_subscriber_with_alert.py`.
4. Run `python scripts/publishers/capstone_stress_publisher.py`.
5. Check Grafana datasource health and run each of the eight dashboard panel queries against this fresh data.
6. Open the dashboard and inspect all eight panels. For a short run, zoom the time range to the run interval.

Use the repository's documented local test configuration for authentication. Do not place a real service credential in notebook output, committed files, URLs, or screenshots.

## Observed results

- Publisher completed its 1,000-payload loop, about 51 seconds.
- Alert subscriber: 171 alert events, zero logged processing errors.
- Grafana database health: OK. Datasource health: OK.
- All eight panel queries: HTTP 200, nonempty frames, no query errors.
- Temperature, humidity, power, current, Isolation Forest flag, threshold flag: 52 timestamps each.
- Hourly alert panel: five nonempty series.
- Latest anomaly status panel: one value (0 at capture).
- Actual dashboard pixels inspected at default and zoomed time ranges: all eight panels show data, no No data or error banners.

The publisher uses second-resolution timestamps. Multiple payloads with the same measurement, device tag and timestamp overwrite field values in InfluxDB. Therefore 1,000 published payloads are not 1,000 distinct stored rows; the 52 timestamps above are not a dropped-message measurement. The hourly alert panel reflects stored points, not a count of all MQTT events.

Original repository scripts and dashboard JSON were not edited. Training regenerated only local runtime model data; the working tree remained clean. No runtime artifacts were committed.
